# plan-to-issues

Turns `plan.md` into GitHub issues that workers can pick up cold. Easiest with `gh`, authenticated,
in a shell this agent can run.

## Steps

1. Read `plan.md`, `AGENTS.md` and `docs/adr/`.
2. Draft the split as a table: title · plan section · scope · done when · blocked by.
   One issue per unit of work.
3. **Stop and show the table to the human.** Publish nothing until they approve it.
4. Ask the human what every issue here must carry (fields, labels, wording), unless it is
   already written down in this session or in the repo.
5. Create each issue in dependency order, so blocked-by can cite real numbers:

   ```sh
   gh issue create --title "<title>" --body-file <tmp.md>
   ```

6. Record every issue URL from gh's output (not from memory) and reply with the list.

Closing one, with the closing comment from AGENTS.md:

```sh
gh issue close <n> -c "<closing comment>"
```

## What every issue carries

Decided by the human who owns this lane (plan morning-digest, 2026-11-03). Step 4 needs no question while this holds.

- Label `plan:<plan name>` (e.g. `plan:morning-digest`).
- Body, in this order:
  1. `Source: plan.md § <n>` as the first line.
  2. **Scope**: what is in, what not to touch.
  3. **Done when**: the plan's condition, word for word.
  4. **Blocked by**: `#n` or `—`.
  5. **Model**: strongest or cheaper, and why in a few words.
- Close only when "Done when" holds. A step that waits on a person (a review) stays open until they have looked.

## No `gh`

Steps 1–4 hold either way. GitHub reachable another way (a connector, the REST API, the web UI):
the same issues, made that way. GitHub issues out of reach altogether: write them as files in
`docs/issues/`, format in ADR 0004, then commit and push.

## Don'ts

- Don't paste the whole plan into one issue, and don't keep issues only in chat.
- Don't invent sections the plan doesn't have. If the plan is unclear, ask.
